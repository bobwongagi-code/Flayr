# 状态异常处置

适用本机 Flayr Web 及批处理，依据`72fa453`。这里没有一键修复或自动重跑命令。先停止新增提交，保留原浏览器会话和任务 ID，再按下表处理；不要求重看视频或补 GT。

## 先做的事

1. 记下任务 ID、错误发生时间、最后一次操作、原终端的错误类型与服务是否仍活着。原始日志只留本机，不粘贴密钥、签名 URL 或完整环境变量到聊天/GitHub。
2. 需要停机时，在启动 Web 的原终端按一次 Ctrl-C，等待原清理流程结束。出现“未完全停止”后不要连续强退、删目录或再开一个服务。批处理同样先核对原 runner 及子进程，不删锁解围。
3. 不把页面`failed`、批次`interrupted`、端口已关闭或终端出现提示，单独当作工作进程已经退出。PID 与任务的关系不明时交维护者核对，不能凭同名 Python/ffmpeg 进程猜测并终止。

## 三种情况

| 情况 | 先核对什么 | 可以怎样重试 | 必须停下的条件 |
| --- | --- | --- | --- |
| 进程未完全停止，或出现`cannot stop` | 原终端错误、维护者核实的任务/进程对应关系和存活状态；同一`JobStore`是否还存在 | 由维护者沿原停机流程处理；仍存活的进程先处理，确认退出再决定是否恢复服务。重新执行停机是清理，不是重新提交分析 | 无法确认 PID 归属、进程仍活、线程池或状态补写继续失败；不要启动第二个服务或新任务 |
| 删除未完成，或删除接口报 500 | 同一任务是否仍在列表，是否显示“删除未完成”；进程是否已停止；剩余文件/写权限/空间是否可用 | 原服务仍可用且环境原因已排除时，用原浏览器、同一任务的删除入口重试一次；可能只是删除剩余文件。它不创建新分析任务 | 仍有进程、再次失败、列表里没有任务但目录还在、或归属不明；不要手工删目录来制造成功 |
| 索引损坏、不可写或恢复模式警告 | 下列索引/元数据是否存在，磁盘剩余空间和文件权限，服务是否已停止；维护者核对实际产物与任务归属 | 先排除空间/权限原因。服务和旧工作进程确认停止、材料已按需保全后，由维护者启动原服务一次，让既有隔离/重建及发布门禁处理，再核对任务数量、归属及失败原因 | 仍报全局索引写失败，或无法隔离损坏索引，或重建后记录/归属不符；不循环重启，不直接拿备份覆盖主索引 |

“只读恢复模式”表示代码禁止覆盖索引，不保证 Web 一定能启动或所有操作可用；后续恢复/清理若需要写索引，启动仍可能失败。失败记录也不保证部分已删文件能够恢复。

## 路径与禁止操作

默认 Web 根是仓库内`runs/_web/`；嵌入式调用可能指定其他根，先核实，不能照抄默认路径处理别的服务。

| 需保留的证据 | 路径或记录 |
| --- | --- |
| 主/备/隔离索引 | `jobs.json`、`jobs.json.bak`、`jobs.json.corrupt-*` |
| 单任务归属与素材 | `jobs/<任务ID>/job.json`、`inputs/`、`worker.log`、`run/` |
| 运行与发布证据 | 任务`run/`中的`run_state.json`、`_SUCCESS.json`、`degraded_manifest.json`及原分析/报告 |
| 浏览器身份 | Web 根的`.client_cookie_secret`或原服务配置的签名密钥；不展示其值，不删除以“重置权限” |
| 批处理归属 | 该批自己的`runner.lock`和`status.json`；默认批次位置见原启动命令，不推定所有批次都在同一目录 |

不编辑状态为`completed`，不补造成功标记，不删除`.bak`/`.corrupt-*`、预处理恢复备份、任务元数据或锁文件，不清 Cookie、不用全盘`chmod`/`sudo`或强杀同名进程绕过问题。

**重启有清理副作用。** 当前启动会清理超过 1 小时的上传暂存；终态任务按`created_at`超过 7 天进入保留期清理，并非“完成后再保留 7 天”。清理会删除整个任务目录，媒体留在原目录不等于已保全。

需要留证时，先由维护者确认服务及工作进程已停，将受影响的索引、归属元数据、状态、清单，以及确实需要保留的输入媒体、截图和报告，复制到原 Web 根及其他自动清理目录之外的任务专属位置；核对必要文件可读、字节一致后，才决定重启。只保全受影响范围，不盲目复制整个`runs/`。空间不足或保全范围不明时，不重启，不通过改时间戳或状态绕过清理。副本含内部资料，不进公开版本库。

## 是否产生新模型调用

| 操作 | 本身是否启动新调用 |
| --- | --- |
| 看原日志、刷新现有列表/详情、核对 PID/空间/权限 | 否；旧的存活工作进程仍可能继续调用，所以必须另核进程是否停止 |
| 停机清理、重试同一任务删除、原服务索引重建 | 不自动提交模型任务；重启仍有上述本地文件清理副作用 |
| 重新上传、再次运行`improve`/`breakdown`、重启批量分析、使用可能在线回退的`resume` | 可能产生新调用，属于新执行；先明确范围和预算授权，不把原来的发送失败或`failed`当作免费重试凭证 |

完成后在原任务记一行：任务 ID、原因、处理人/时间、实际操作、进程退出是否确认、索引与文件核对结果、是否有新增调用或仍未知。只有这些核对完成，才恢复新提交；有未确认项就交维护者，不写“已修复”。

机制与回归依据见[开发维护说明](../DEVELOPMENT.md#web-停机边界)、[逐项对账](state-governance-ledger.md)。本说明只定义处置边界，没有验证真实断电或多进程恢复。
