# ADR-007：证据优先分析流水线冻结方案

**状态：Accepted / Design Frozen**  
**日期：2026-08-07**  
**适用范围：Stage1 证据采集、Stage1 到 Stage2 交接、Stage2 阶段判断、局部修复、结果收口与评估**

## 1. 决策摘要

Flayr 不再通过继续扩充单次大模型合同来解决证据不充分、交接丢失和后续判断失败。目标架构冻结为以下原则：

1. 保留小型、可独立验证的结构化判断，不以“减少约束数量”为目标。
2. 降低一次模型调用同时承担的独立判断数量，不再让一次调用完成六阶段、四渠道、来源对账、证据链接、严重度和建议生成。
3. Stage1 建立不可变的原子证据账本。阶段资格失败不得删除、覆盖或隐藏已观察到的事实。
4. Stage1 将“观察事实”和“事实属于哪个阶段、是否够资格”拆成两个步骤。
5. 缺失证据只触发目标窗口、目标渠道、目标阶段的有限补观察，不重新运行整条 Stage1。
6. Stage1 到 Stage2 使用双通道交接：正式判断只能消费合格证据；候选证据和缺失原因必须保留并可审计。
7. Stage2 按紧耦合的小阶段组分别判断，不再输出完整分析大对象。
8. 模型只负责语义观察和判断。证据 ID、时间归一化、链接投影、字段来源、最终 severity 和运行状态由确定性代码负责。
9. repair 只能修改目标阶段的允许字段，禁止整对象重写和跨阶段修改。
10. 单阶段失败必须被隔离。它可以让该阶段成为 `unknown` 或让运行成为 `degraded`，不能抹掉其他阶段的有效结果。
11. 报告是只读投影，不能修改分析事实和判断。
12. 先用离线重放和小规模端到端门禁证明系统可完成，再运行 new12 和历史 16 组。不得用昂贵的全链路重跑验证纯确定性改动。

本 ADR 不针对 Aavini 或当前 9 个样本编写样本特例。Aavini 仅作为能够稳定暴露系统级问题的回归样本。

## 2. 为什么冻结这个方向

### 2.1 已确认的问题

当前流水线把多种不同职责压入同一次 Stage2 调用：

- 六个阶段的双方判断；
- 视觉、口播、字幕和音频的综合；
- S5 来源分类与可信度；
- `stage_evidence_links`；
- severity、总结、改善建议和全局结论；
- 大量机械格式字段。

只要其中一个局部字段失败，现有流程可能重新生成整个大对象。新结果又可能破坏原本正确的字段，形成“修一个、再坏一个”的重试放大。

Stage1 也存在两个长期问题：

1. 首次观察没有稳定捕获决定性事实。
2. 已观察到的事实如果未通过阶段资格检查，会在面向 Stage2 的视图中被清空或降为只有状态、没有完整内容的信息。

因此，Stage2 经常同时面对“必须输出完整结论”和“没有拿到足够证据”两个冲突要求。模型只能猜测、补全或生成无法通过来源校验的字段。

### 2.2 Aavini 回归说明了什么

人工判断认为 Aavini 的决定性差距集中在 S3 和 S4：标杆的涂抹过程与效果展示更充分，达人画面焦点弱，效果不清楚。

近期 Stage1 结果却将达人 S3-S6 多个阶段记为 `unknown`，标杆 S4 也未形成可用正式证据。后续 Stage2 仍被要求补齐 S1-S6、multimodal、S5 来源和链接，最终在 S5 来源与多模态证据校验中连续失败，整次运行没有生成 `_SUCCESS.json`。

这说明当前问题不是某一条严格校验规则错误，而是以下组合错误：

```text
证据没有充分采集
    + 阶段资格失败后产生信息断崖
    + Stage2 仍承担完整大合同
    + 整对象 repair 扩大故障范围
    = 局部证据问题升级为整次运行失败
```

### 2.3 不采纳的归因

不采纳“结构化约束本身有害”这一归因。历史结果已经显示，小型且可单独校验的结构化判断有价值，例如 S1 landing 条件拆解、S3/S4 四态和判断前简短依据。

真正的问题是约束的形状和所有权：

- 太多独立判断在一次调用中原子提交；
- 语义判断、机械整理和最终裁决混在一起；
- repair 权限过大；
- 局部失败没有被隔离。

## 3. 目标与非目标

### 3.1 目标

1. Stage1 对人工认定的核心事实具备可测量的召回率和精确率。
2. 任一已采集事实从 Stage1 到最终分析均可通过 ID、时间、渠道和哈希追溯。
3. 不合格候选事实不会支撑 severity，但不会从系统中消失。
4. Stage2 在证据充分时做聚焦判断，在证据不足时明确返回 `unknown`，不补写伪事实。
5. 一个阶段的格式或语义失败不触发其他阶段重跑。
6. 所有最终字段只有一个写入者。
7. 离线规则改动可离线验证；真实模型调用只用于模型行为和完整链路验证。
8. 完成状态能够真实区分 `completed`、`degraded`、`failed`、`not_run` 和人工中止。

### 3.2 非目标

本 ADR 不包含：

- 新的模型选型结论；
- 将 VL 模型提升为主模型；
- 修改已经冻结的 floor/ceiling resolver 数学规则；
- 放松证据来源、时间或渠道校验；
- 修改 human initial GT 协议；
- 新的报告 UI；
- 云部署和多人权限设计；
- 针对 Aavini、S4 或当前 9 个样本写死规则。

VL 单视频事实抽取继续作为独立适配器工作线。它必须输出同一证据账本合同，不能建立第二套 `evidence_strength`、时间或阶段状态语义。

## 4. 目标架构

```text
原始视频、Fun-ASR、OCR、镜头与音频轨
                    |
                    v
        Stage1-A 原子证据采集
        不可变 Evidence Ledger
                    |
                    v
        Stage1-B 阶段投影与资格检查
                    |
          +---------+----------+
          |                    |
          v                    v
   qualified_evidence   candidate_observations
   可支撑正式判断        保留但不可支撑 severity
          |                    |
          |          Stage1-C 定向缺口补观察
          |                    |
          +---------+----------+
                    |
                    v
        Stage2 小阶段组独立判断
      S1+S2 / S3+S4 / S5 / S6
                    |
                    v
       确定性投影、校验与 resolver
                    |
          +---------+----------+
          |                    |
          v                    v
  Stage3 建议与全局综合      局部 patch repair
  只读已锁定阶段结论        只改目标阶段允许字段
          |                    |
          +---------+----------+
                    |
                    v
        Finalizer -> reports / manifest
```

数据流必须单向。Stage2、Stage3、repair 和报告均不得回写 Evidence Ledger。

## 5. Stage1-A：不可变原子证据账本

### 5.1 采集职责

Stage1-A 只回答“视频中在什么时间、通过什么渠道、观察到了什么”。它不回答：

- 该事实属于哪个阶段；
- 双方谁更好；
- 差距大小；
- severity；
- 商业优先级；
- 改进建议。

### 5.2 原子证据最小合同

每个证据单元至少包含：

| 字段 | 写入者 | 规则 |
|---|---|---|
| `evidence_id` | 确定性代码 | 同一运行内唯一、稳定、不可由模型自由命名 |
| `video_role` | 编排代码 | `benchmark` 或 `creator` |
| `start_seconds` / `end_seconds` | 模型候选，代码归一化与校验 | 不允许负数、反向、非有限值或越界 |
| `channels` | 模型选择，代码校验 | `visual`、`speech`、`text`、`audio` 的受限集合 |
| `observation` | 模型 | 只写可观察事实，不写比较和结论 |
| `source_refs` | 模型选择，代码校验 | 只能引用实际存在的帧、ASR、OCR 或音频片段 |
| `evidence_strength` | 模型，代码检查 | 正证据只允许 `direct`、`explicit`、`inferred`；`absent` 不创建正证据单元 |
| `source_fingerprint` | 确定性代码 | 绑定源视频、预处理版本和轨道哈希 |
| `capture_attempt_id` | 编排代码 | 可追踪首次采集或定向补观察 |

`Evidence Ledger` 为 append-only。任何后续步骤只能新增证据、增加资格和引用关系，不能修改或删除原始证据内容。

### 5.3 覆盖机制

不再用“最多 12 条证据”或其他固定数量表示采集完整。数量只属于资源预算，不属于语义完成条件。

覆盖状态来自两类清单：

1. 时间覆盖：镜头边界、ASR/OCR 边界、Hook/CTA 加密窗口形成 canonical windows。
2. 业务覆盖：`stage-evidence-contract.md` 和产品卖点计划定义每阶段必须寻找的证据槽位。

每个槽位必须得到一个显式结果：

```text
captured
explicit_absence
uncertain
not_observable
budget_exhausted
```

没有返回字段不是 `explicit_absence`。模型自称“完整”也不能替代代码对覆盖槽位的检查。

安全预算继续由运行级字节、时长、调用次数和成本上限控制。达到预算时必须写 `budget_exhausted`，不得静默截断后宣称采集完成。

## 6. Stage1-B：阶段投影和证据资格

Stage1-B 读取 Evidence Ledger，将证据映射到 S1-S6 的候选槽位。它不改变原始事实。为隔离故障，资格化请求固定拆为 `S1+S2 / S3+S4 / S5 / S6` 四个独立阶段组，与 Stage2 的边界一致；一个阶段组失败只将该组置为 `unknown`，不能清空其他组已经形成的资格结果。

每个角色、每个阶段输出：

- `candidate_evidence_ids`；
- `qualified_evidence_ids`；
- `stage_readiness`：`present | absent | unknown | conflict | not_applicable`；
- `required_signal_bindings`；
- `missing_requirements`；
- `evidence_strength`：`direct | explicit | inferred | absent`；
- `projection_reason_code`；
- 输入账本哈希和投影版本。

Stage1-B 的代码元数据同时记录每个阶段组的请求状态、产物引用和失败原因。`status=completed` 只表示四组请求已经收口，不表示每个阶段都有资格证据；阶段可用性必须读取各阶段的 `stage_readiness`。

硬规则：

1. `present` 只能由 `direct` 或 `explicit` 支撑。
2. `inferred`、缺字段和来源冲突均不能触发 floor。
3. `absent` 必须建立在相关窗口与渠道确实可观察、且完成检查的基础上。
4. 同一证据可以成为多个阶段的候选，但每个正式引用必须单独通过阶段资格检查。
5. `unknown` 和 `conflict` 不能清空 `candidate_evidence_ids`。
6. 阶段投影结果不直接写 severity。

## 7. Stage1-C：定向缺口补观察

只有以下情况允许进入补观察：

- 必需槽位为 `unknown`；
- 候选事实存在但时间、渠道或来源无法确认；
- 双侧决定性事实不对称，且缺失一侧仍有可观察原始媒体；
- hard-fact 之间出现机械冲突。

补观察必须满足：

1. 只重看目标视频、目标时间窗和目标渠道。
2. 使用与首次全片观察不同的聚焦视图，例如原生视频切片、词级转写窗口、OCR 时间轨或关键镜头段。
3. 结果只能追加 Evidence Ledger，再重新运行目标阶段投影。
4. 每个角色、每个阶段最多一次补观察。
5. 补观察后仍不足时保持 `unknown` 或 `conflict`，不继续递归重试。

这一步替代当前“用同一大 payload 重新做一次 coverage audit”的方式。相同媒体表示和相同大问题容易复现同一盲区，不能被视为真正独立检查。

## 8. Stage1 到 Stage2 的双通道交接

交接对象包含：

```text
ledger_ref + ledger_hash
qualified_evidence_by_stage
candidate_observations_by_stage
stage_readiness
missing_requirements
coverage_summary
source_fingerprints
```

使用规则：

- `qualified_evidence` 可以进入模型正式判断并支撑 model gap。
- `candidate_observations` 必须保存在交接产物中，但不能支撑 relation、gap 或 severity。
- Stage2 prompt 只接收目标阶段的合格证据、候选状态摘要和缺失原因，不把完整候选账本再次塞入模型上下文。
- 候选事实只能用于解释“为什么无法判断”或触发 Stage1-C，不能被 Stage2 自行升级为正式证据。
- 交接前后必须校验证据数量、ID 集合和 ledger hash，信息保存率必须为 100%。

这同时避免两个极端：既不让不合格证据污染判断，也不让它们从系统中消失。

## 9. Stage2：小阶段组独立判断

Stage2 固定拆为四个独立判断单元：

1. S1 + S2：Hook 与承接存在直接因果关系。
2. S3 + S4：使用过程与效果证明构成连续因果链。
3. S5：来源、背书与信任语义独立处理。
4. S6：CTA 独立处理，可只读 S4 的效果证明摘要，不得修改 S4。

四个单元允许并行。任一单元失败不得使其他单元重跑或失效。

### 9.1 每阶段模型输出

每个阶段只输出：

- 阶段专属事实状态；
- `relation`：`creator_better | benchmark_better | equivalent | uncertain`；
- `model_gap_magnitude`：`none | small | medium | large | uncertain`；
- 简短判断依据；
- 实际使用的合格证据 ID；
- 模型自报不确定性，仅作诊断，不单独获得裁决权。

阶段专属事实状态继续保留已有的小型结构化合同：

- S1 使用已定义的 landing 条件；
- S3 使用 `none | partial | complete | uncertain`；
- S4 使用 `none | result_only | verified | uncertain`；
- S5 使用已冻结的来源四态，继续保持 audit-only，直到独立 promotion 门槛通过；
- S2、S6 使用当前已存在的阶段合同，不在本 ADR 中重新发明平行语义。

模型必须先完成事实状态和双方关系，再给 `model_gap_magnitude`。理由必须引用已经选择的合格证据，不能在给出结论后新增事实。

### 9.2 Stage2 不再输出

以下字段从 Stage2 模型合同中移除：

- `stage_evidence_links`；
- 证据 ID 生成和格式整理；
- 最终 `severity`；
- 全局 `commercial_priority`；
- 完整 `improvements`；
- 报告文案；
- 运行状态；
- 其他阶段的修复字段；
- 可由已有事实确定性推导的 multimodal 和来源投影。

## 10. 确定性投影和唯一写入者

每类字段必须只有一个权威写入者：

| 字段类别 | 权威写入者 | 其他组件权限 |
|---|---|---|
| 原始语义观察 | Stage1-A 模型 | 只读 |
| ID、时间、来源哈希、渠道可用性 | 确定性代码 | 模型只能给候选 |
| 阶段候选与资格 | Stage1-B projector | Stage2 只读 |
| 阶段事实状态、relation、model gap、理由 | 对应 Stage2 判断单元 | repair 只能按允许路径局部修正 |
| `stage_evidence_links` | 确定性 projector | 模型不能输出 |
| S5 来源类型与可追溯性事实 | Stage1 typed facts + 确定性校验 | Stage2 只判断相关性和作用 |
| floor/ceiling 与最终 severity | resolver | 模型和 repair 不可写 |
| 全局优先级和改进建议 | Stage3 synthesis | 不可改阶段事实和 severity |
| report HTML | renderer | 只读最终分析 |
| run state 与 `_SUCCESS.json` | finalizer | 其他组件只能上报状态 |

`stage_evidence_links` 必须从 Stage2 实际使用的证据 ID 和 Stage1 资格结果生成。链接不完整是确定性代码错误，不再通过模型重跑修复。

## 11. Stage3：建议和全局综合

Stage3 读取已经锁定的阶段结果，输出：

- 全局诊断；
- 商业优先级；
- BD/内部版沟通材料；
- 达人版改进建议所需的内容数据。

Stage3 可以使用模型进行综合，但必须满足：

1. 不能改变 Stage1 事实、Stage2 relation、model gap 或 resolver severity。
2. 每条建议必须指向已经存在的阶段结论和证据 ID。
3. Stage3 失败只影响建议与报告完整度，不得倒推重跑 Stage1/Stage2。
4. report renderer 只负责展示，不负责补事实或修正判断。

## 12. 局部 repair 合同

禁止任何组件返回或替换完整 `analysis`、完整 `stage_analysis` 或其他阶段对象。

repair 输入固定为：

- 目标阶段；
- 失败的字段和错误代码；
- 允许修改的 JSON Pointer；
- 锁定的合格证据；
- 修改前快照哈希。

repair 输出只能是允许路径的 patch。应用规则：

1. 任一越界路径导致整个 patch 被拒绝。
2. ledger、其他阶段、final severity、recommendations 和报告字段不可修改。
3. 合法 patch 应重新运行目标阶段的 repair、validate 和 resolver 链。
4. 目标阶段最多一次 repair。
5. repair 后仍失败，目标阶段变为 `unknown` 或运行变为 `degraded`，不进行整对象重写。
6. patch 前后快照使用统一 schema，记录实际变更路径和 resolver 前后结果。

如果 S1+S2 或 S3+S4 同组返回，校验和 repair 仍按单阶段隔离。一个阶段有效时必须保存，不能因同组另一阶段失败而丢弃。

## 13. 失败和完成语义

### 13.1 阶段状态

每个阶段最终为：

```text
completed
unknown
conflict
not_applicable
failed
```

- `unknown` 表示证据不足，不产生真实 severity。
- `conflict` 表示证据或规则冲突，不得强行裁决。
- `not_applicable` 必须有明确适用性依据，不能用来隐藏缺失。
- 非核心诊断字段缺失不阻断核心阶段，字段保持 unknown。
- 核心证据缺失时，该阶段不得伪装为 completed。

### 13.2 运行状态

- 所有适用的核心阶段完成，必要产物通过哈希校验，才可写 `_SUCCESS.json` 和 `completed`。
- 核心阶段存在 `unknown`、`conflict` 或 `failed` 时，可在显式允许降级的模式下生成部分报告，但运行状态必须为 `degraded`，不能写成功清单。
- 外部 API、资源预算或媒体处理失败必须保留原始失败原因。
- 人工终止固定写为 `aborted_by_operator`，不能计入模型准确率或合同失败率。
- `not_run` 和 `degraded` 不产生伪造的 medium severity。

## 14. 评估和错误归因

### 14.1 分层错误分类

每个不一致样本必须定位到最早失败层：

1. `acquisition_miss`：Stage1 未观察到 GT 核心事实。
2. `temporal_or_channel_error`：观察到内容，但时间或渠道错误。
3. `stage_projection_error`：事实存在，但阶段归属或资格错误。
4. `handoff_loss`：Stage1 有事实，Stage2 交接中丢失。
5. `judgment_error`：证据充分，Stage2 relation 或 gap 错误。
6. `resolver_error`：模型判断正确，确定性收口改错。
7. `repair_regression`：repair 破坏原本正确字段。
8. `report_projection_error`：分析正确，报告展示错误。

`judgment_error` 继续区分：

- 方向错误；
- 档位错误；
- GT 边界或口径分歧。

方向错误单独统计，不能和差一档的校准误差等权处理。

### 14.2 必须报告的指标

Stage1：

- 人工核心事实召回率；
- 证据精确率；
- 时间范围准确率；
- 渠道归属准确率；
- 阶段投影召回率和精确率；
- `unknown`、`conflict`、`budget_exhausted` 比率；
- 定向补观察新增有效事实的 yield；
- 交接证据保存率，目标为 100%。

Stage2 和系统：

- 证据充分条件下的 relation 和 gap 准确率；
- 方向错误率；
- 两档错误数；
- first-pass 阶段完成率；
- 每阶段 repair 率；
- 重试放大率；
- 单样本调用次数、输入输出 token、延迟和费用；
- run-level `completed`、`degraded`、`failed` 比率；
- 最终 GT 准确率。

不得只报告最终准确率。否则无法判断提升来自证据采集、判断、resolver，还是记账口径变化。

## 15. 验证顺序和门禁

### 15.1 冻结输入离线重放

确定性字段来源、链接生成、projector、resolver、repair 权限和报告投影，必须优先使用已保存的 Stage1/Stage2 原始输出离线重放。

离线重放不得调用模型，必须保存输入文件哈希、代码提交、schema/prompt 版本和输出差异。纯确定性变化没有通过离线重放前，不允许用新一轮完整模型运行代替验证。

### 15.2 自动化不变量

必须覆盖：

1. Evidence Ledger append-only，内容哈希不可变。
2. Stage1-B 不可修改或删除账本证据。
3. Stage1 到 Stage2 的 ID 集合和账本哈希保存率为 100%。
4. candidate evidence 不得影响 relation、model gap、floor、ceiling 或 final severity。
5. `present` 不接受 inferred、missing 或 absent 作为正证据。
6. 缺字段与 uncertain 分开记录。
7. repair 越界路径全部拒绝。
8. 合法 patch 会重新运行目标阶段校验和 resolver。
9. 同组一个阶段失败时，另一个阶段保持字节级不变。
10. `stage_evidence_links` 完整、唯一并只引用合格证据。
11. 报告生成前后 analysis hash 不变。
12. 子阶段失败不会触发其他阶段或整次 Stage2 重跑。

### 15.3 小规模端到端技术门禁

在运行 new12 和历史 16 组前，先运行：

- Aavini；
- 两个未被历史异常专门挑选的普通样本；
- 三个样本固定视频、配置、模型和 prompt/schema 版本。

通过条件：

1. 所有请求阶段都产生 schema-valid 结果或显式 typed unknown。
2. 单阶段问题不会造成 run-level opaque failure。
3. 不发生完整 Stage2 对象重试。
4. repair 不修改目标阶段以外的任何路径。
5. Stage1 到 Stage2 的账本保存率为 100%。
6. 不允许无证据来源或错误渠道的声明通过校验。
7. 结果相对冻结基线不得新增方向反转或两档错误。
8. 每个阶段最多一次初始判断和一次局部 repair。
9. 运行能够生成真实 completed 或可解释 degraded，不得卡在不一致中间状态。

### 15.4 数据验证

技术门禁通过后，按以下顺序执行：

1. new12 的 12 对全新样本用于模型和完整链路盲测。
2. 历史 16 组只用于 `mechanism_regression`，不能用于 promotion 调参。
3. 两批数据分别报告，不合并成一个 headline 准确率。
4. 没有 GT 的阶段不计对错；合同失败和模型判断错误分开统计。
5. 沿用现有晋级红线：至少 12 对独立 blind、4 个品类、2 个市场；总准确率不低于 80%，单阶段不低于 70%，两档错误为 0，Stage1 决策事实召回和 Stage2 使用率均不低于 90%，Phase C 不得引入回归。

### 15.5 人工 GT、模型分歧与模型选型

人工 GT 与模型结果必须分成两个层次，不能用一张表强迫人工以模型的顺序思考：

1. **`human_initial` 先冻结**：人工先看完整视频，记录整体判断、S1-S6 的方向与差距、`not_applicable`/`uncertain`、关键事实和理由；此时不得查看模型结果。
2. **事实层与结论层分开**：关键事实记录用于抽取召回和证据归属核对；整体判断用于 relation/gap 对照。人工的整体印象可以帮助定位回看位置，但不能替代事实核验。
3. **模型理由不是裁判证词**：模型提出人工未记录的新事实时，必须回看原视频独立核实；核实为真才修正 GT，并记录“人工遗漏”；核实为假则保留 GT，并记录模型事实错误。
4. **纯权重分歧不靠说服解决**：双方事实相同、只对差距大小或购买影响判断不同的情况，进入第二人工盲标或标记为校准分歧，不以模型理由的流畅度决定胜负。
5. **一致也要保留归因**：一致结果要区分“初始判断即正确”“后续结构化约束纠正”“无效机制下碰巧一致”，不得只累计一个最终准确率。
6. **模型选型不得使用 seen 样本拍板**：历史 16 组只能做 `mechanism_regression`，已打开结果的 new12 或校准样本只能做诊断。模型抽取与判断能力必须可分别测量；VL 只能作为同一 Evidence Ledger 合同下的独立单视频适配器验证，不能因单样本或格式通过率直接晋升主模型。
7. **promotion 前必须同一合同公平比较**：候选模型在同一批冻结视频、同一输入身份、同一 prompt/schema、同一预算下比较；raw extraction、judgment-only、端到端结果、运行失败、成本、延迟和重复稳定性分开报告。

人工 GT 的详细字段和离线评分口径以 `references/model-selection-evaluation-protocol.md` 为配套合同；本 ADR 的数据流、所有权和失败语义优先于任何评估脚本的兼容投影。

## 16. 分阶段实施方案

每一阶段都必须独立可合并、可运行；不得建立长期并存的两套业务语义。

### Phase 1：字段所有权和交接损失审计

改动范围：

- 为现有 schema 每个字段声明 `model_fact`、`model_judgment`、`deterministic_projection` 或 `diagnostic_only`。
- 增加 Stage1 到 Stage2 的证据 ID、数量和哈希差异审计。
- 不改变现有模型 prompt 和正式结果。

验收：当前流水线行为不变，所有 schema 字段有唯一所有者，交接中被过滤的事实能够被完整报告。

独立价值：即使后续阶段暂停，也能准确测出证据丢失发生在哪里。

### Phase 2：Evidence Ledger、阶段投影和定向补观察

改动范围：

- Stage1-A 只产原子事实。
- Stage1-B 独立完成阶段投影与资格。
- Stage1-C 对缺失槽位做一次定向补观察。
- 通过单一 compatibility adapter 向现有 Stage2 提供旧格式输入。

验收：账本不可变、候选不丢失、缺口状态显式、交接保存率 100%，现有报告仍可生成。

独立价值：即使 Stage2 尚未拆分，证据采集和交接质量已经可测且可改善。

### Phase 3：拆分 Stage2 和确定性字段投影

改动范围：

- Stage2 拆为 S1+S2、S3+S4、S5、S6 四个判断单元。
- 机械字段从模型合同移出。
- `stage_evidence_links`、时间与来源投影由代码生成。
- Stage3 建议综合读取锁定阶段结果。
- 新路径暂不使用模型 repair；首次失败直接产生 typed unknown/degraded。

验收：四个判断单元可独立完成和失败；Aavini 不再因一个 S5/multimodal 字段导致整次 Stage2 重跑；现有两类报告通过 adapter 正常展示。

独立价值：即使 Phase 4 不实施，系统也能以明确 degraded 结果稳定运行，不再出现整对象 repair 回归。

### Phase 4：局部 repair 和阶段隔离

改动范围：

- 增加受控 JSON Pointer patch。
- 按阶段保存前后快照。
- 仅重跑目标阶段校验和 resolver。

验收：非法 patch 100% 拒绝，合法 patch 正常生效，其他阶段字节级不变，每个阶段最多一次 repair。

独立价值：在 Phase 3 的稳定降级基础上恢复有限自愈能力，不扩大故障范围。

### Phase 5：正式切换和旧路径删除

改动范围：

- 通过小规模技术门禁和 new12 blind 后，将新流水线设为唯一生产路径。
- 删除旧 Stage2 大合同、旧整对象 repair 和仅为双路径兼容存在的 adapter。
- 更新 `ARCHITECTURE.md`、schema、运行清单和评估文档。

验收：旧路径不再可调用；所有生产结果记录新 pipeline、prompt、schema 和 projector 版本；完整测试、new12 和历史 16 组机制回归通过既定门槛。

独立价值：结束临时双路径，降低未来维护成本和语义漂移风险。

## 18. 依赖、成本和扩展风险

### 18.1 外部依赖

- 视频预处理继续使用 ffmpeg/ffprobe。
- 口播继续使用北京 MaaS Fun-ASR。
- OCR 继续使用现有在线 OCR 路径。
- 语义观察和判断继续使用当前获准的 Qwen/DashScope provider profile。

实现和离线验证不需要新增密钥。端到端门禁和 blind cohort 需要现有可用的 Qwen/DashScope key 和调用额度。

### 18.2 成本控制

Stage2 从一次大调用变成四个小调用，调用次数增加，但可以并行。成本目标不是“调用最少”，而是：

- 总输入输出 token 不高于旧大合同加重试的稳定分位；
- 不出现整对象三次重跑；
- 单阶段只为自身失败付重试成本；
- Stage1-C 只为真实缺口付一次定向调用成本。

费用、token 和延迟必须作为 promotion 指标，不允许准确率提升后再补做成本评估。

### 18.3 最脆弱的前提

本方案假设当前原生视频、ASR、OCR、镜头和音频输入足以让至少一个抽取模型稳定观察到人工认定的核心事实。

如果这个前提不成立，Stage1-B 和 Stage2 再正确也会持续缺证据。方案通过以下方式避免架构失效：

- 账本合同与具体抽取模型解耦；
- 明确测量核心事实召回率；
- 允许对缺口做一次不同视图的定向补观察；
- 抽取器可以替换为 Qwen、VL 单视频适配器或其他模型，而不改变下游合同；
- 无法观察时保留 unknown，不制造假成功。

## 19. 回滚和数据兼容

1. 所有新产物写新的 pipeline/schema 版本，不覆盖历史结果。
2. Phase 2 至 Phase 4 使用一个临时的 pipeline version 开关做发布切换，不允许出现按字段混用新旧语义的多个开关。
3. 任一阶段回滚均通过代码回退和选择旧 pipeline version 完成，不需要改写历史数据。
4. Phase 5 删除旧路径前必须保留可读旧产物的只读解析能力；旧产物不得被重新解释成新合同结果。
5. Phase 5 完成后不再长期维护双生产路径。回滚只允许回滚整个发布版本，不恢复局部旧逻辑。

## 20. 与现有决策的关系

- `ADR006.md` 的 Phase C qualification、scope、预算和 patch 权限继续有效。本 ADR 只改变 Phase C 之前的数据形状和执行粒度。
- floor/ceiling resolver 继续保持“模型判断默认保留，约束只能收窄”的规则。
- S5 继续为 audit-only，直到其独立边界卡、稳定性和 blind promotion 门槛通过。
- S6 CTA ceiling 的历史小样本收益不构成通用有效性证明。
- 当前 `ARCHITECTURE.md` 描述实际生产状态。本 ADR 描述已冻结的迁移目标；每个 Phase 合并时必须同步更新实际状态，不能提前把未落地设计写成现状。

## 21. 当前执行冻结

在 Phase 1 至 Phase 3 技术门禁完成前：

- 不继续运行 new12 全批；
- 不运行历史 16 组做准确率 headline；
- 已被人工中止的运行标记为 `aborted_by_operator`，不得计入模型失败；
- Aavini 只用于离线回放和小规模技术门禁，不据此调单样本规则；
- 不继续扩大模型选择矩阵；
- 不通过放松严格证据校验来换取表面完成率。

## 22. 最终验收定义

只有同时满足以下条件，才能认为本冻结方案落地完成：

```text
1. Stage1 原子事实账本不可变，交接保存率为 100%。
2. 缺失、未知、冲突、明确不存在和预算耗尽被分别表达。
3. 不合格候选事实不会支撑判断，但不会从系统中消失。
4. Stage2 不再输出机械字段和完整分析大对象。
5. 四个阶段判断单元可以独立成功、失败和局部修复。
6. 任何 repair 都不能修改非目标阶段、ledger 或 final severity。
7. 单阶段失败不会导致整条 Stage2 重跑或其他阶段结果丢失。
8. 最终 severity 只有 resolver 一个写入者。
9. 报告生成不会改变 analysis 内容。
10. Aavini 与两个普通样本通过小规模技术门禁。
11. new12 blind 和历史 16 组机制回归按不同口径完成。
12. 证据召回、判断准确率、完成率、成本和失败类型均可分层审计。
13. 旧 Stage2 大合同和整对象 repair 已从生产路径删除。
```

## 23. 冻结结论

Flayr 的下一步不是继续给模型增加字段，也不是简单删掉所有结构化约束。冻结方向是：

```text
原子事实完整保存
-> 阶段资格独立投影
-> 缺口定向补观察
-> 小阶段组聚焦判断
-> 机械字段代码生成
-> resolver 唯一裁决
-> repair 只做局部 patch
-> 报告只读展示
```

后续实现不得重新引入以下三类路径：

1. 单次调用原子提交六阶段完整分析大对象；
2. 阶段资格失败后从交接中静默删除已观察事实；
3. 为修复局部错误而重写完整阶段集合或完整分析对象。

**本方案冻结。实现应按 Phase 1 至 Phase 5 顺序推进，每个 Phase 单独 review、验证和提交。**
