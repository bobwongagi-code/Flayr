# ADR-006

**状态：Accepted / Design Frozen**
**日期：2026-07-26**

## 1. 决策摘要

Flayr 采用以下合同：

1. Severity resolver 只输出 resolver 自己发现的原始 Phase C 信号，不负责聚合全局候选。
2. 所有来源的原始信号由 provisional finalization 汇总。
3. `LEGACY_V1` 保持当前 Phase C 行为，用于 PR-0A-Core 和即将执行的 blind cohort。
4. `CORROBORATED_V2` 才启用结构化资格判断、Tier 1/2/3、review scope 和预算规划。
5. V2 的合格原因使用判别联合；`reason_code` 与 `tier` 的合法组合由具体类型固定。
6. 模型自报低置信不能单独生成 V2 合格原因。
7. Phase C 预算属于静态 policy；分配属于 plan；执行消耗属于 append-only ledger。
8. provisional pass 可以生成候选；final pass 的返回类型不包含候选。
9. 每个 Run 最多只有一个逻辑 Phase C 回看轮次。
10. Tier 1 因预算不足未执行时，默认降级发布，不因资源预算单独阻断报告。
11. PR-0A-Core 只实现兼容 facade，不实现 V2 planner、ledger 或新候选语义。
12. V2 只有在 fresh blind 结果证明 Phase C 候选选择或预算是主要缺口时才实施。

# 3. 原始 Phase C 信号

原始信号是 qualification 之前的观测结果。它允许信息不完整，因此刻意不承担 reason/tier 类型安全。

```
@dataclass(frozen=True, kw_only=True)
class RawPhaseCSignal:
    signal_id: SignalId
    stage_id: StageId
    origin: PhaseCSignalOrigin
    signal_code: RawPhaseCSignalCode

    fact_ids: tuple[FactId, ...] = ()
    evidence_ids: tuple[EvidenceId, ...] = ()
    constraint_evaluation_ids: tuple[
        ConstraintEvaluationId, ...
    ] = ()
    affected_conclusion_ids: tuple[ConclusionId, ...] = ()
    admissible_severities: tuple["Severity", ...] = ()
```

硬约束：

- raw signal 不能直接进入 V2 planner；
- raw signal 必须先经过 candidate qualifier；
- `MODEL_SELF_REPORT` 可以存在于 raw signal；
- `MODEL_SELF_REPORT` 不能成为 qualified reason 的 qualifying origin；
- raw signal ID 在一个 provisional result 内必须唯一；
  -所有 ID tuple 必须 canonicalize：去重并稳定排序。

# 4. Phase C Review Scope

```
@dataclass(frozen=True, kw_only=True)
class PhaseCReviewScope:
    fact_ids: tuple[FactId, ...]
    evidence_ids: tuple[EvidenceId, ...]
    constraint_evaluation_ids: tuple[
        ConstraintEvaluationId, ...
    ]
    allowed_patch_paths: tuple[PatchPath, ...]
```

不变量：

1. scope 至少包含一个 fact、evidence 或 constraint evaluation。
2. `allowed_patch_paths` 必须来自受控 patch contract。
3. 不允许 `*`、父路径或任意 stage 根级重写。
4. scope 必须 canonicalize。
5. Phase C 返回的每一个 patch path 都必须属于 allocation 的 `allowed_patch_paths`。
6. 任一越界 patch 应被拒绝，不能只忽略越界字段后继续接受其余部分。

# 5. Qualified Phase C Reason：最终判别联合

## 5.1 公共基类

```
@dataclass(frozen=True, kw_only=True)

    reason_id: ReasonId
    stage_id: StageId

    qualifying_signal_id: SignalId
    qualifying_origin: PhaseCQualifyingOrigin
```

- `qualifying_signal_id` 必须包含在 `supporting_signal_ids` 中；
- qualifying signal 必须是非模型来源；

- 所有 supporting signals 必须属于同一 stage；
- 模型信号与 qualifying signal 必须具有 fact 或 evidence scope 交集；
- `affected_conclusion_ids` 用于通过固定 registry 推导 structural impact，不能由规则自由填写 impact 分数。

## 5.6 权威联合类型

```
QualifiedPhaseCReason: TypeAlias = (
    StateConflictReason
    | FloorCeilingConflictReason
    | UncertainFactBoundaryReason
    | InsufficientStrengthStructuralReason
)
```

没有独立的通用 `QualifiedPhaseCReason` dataclass。

### 序列化规则

JSON 中可以输出：

```
{
  "reason_code": "state_conflict",
  "tier": 1
}
```

但解析时：

1. 只使用 `reason_code` 选择具体 dataclass；
2. `tier` 被视为冗余校验字段；
3. 序列化 tier 与具体类型固定 tier 不一致时，整个 reason 解析失败；
4. 禁止通过通用构造器绕过具体类型。

# 6. 模型自报资格规则

在 `CORROBORATED_V2` 下，模型自报低置信只能作为辅助信号。

构造 qualified reason 必须同时满足：

1. 至少有一个非模型结构性信号；
2. 非模型信号本身已经满足四个 reason 类型之一；
3. 模型信号与非模型信号属于同一个 stage；
4. 两者引用相同 fact，或者 evidence scope 有明确交集；
5. tier 完全由非模型结构性信号对应的 reason 类型确定；
6. 模型自报不能提高 tier；
7. 无独立结构性信号时，模型信号进入 `observed_only_signal_ids`，不进入候选池。

结果如下：

```
模型低置信
+ 无独立结构性信号
→ observed only

模型低置信
+ 同 stage、同 scope 的 state conflict
→ StateConflictReason / Tier 1

模型低置信
+ 不同 stage 的结构性信号
→ 不关联

模型低置信
+ 同 stage、无 fact/evidence 交集
→ 不关联
```

# 8. Stage 级候选聚合

```
@dataclass(frozen=True, kw_only=True)
class PhaseCCandidate:
    candidate_id: CandidateId
    stage_id: StageId
    reasons: tuple[QualifiedPhaseCReason, ...]

    @property
    def effective_tier(self) -> PhaseCTier:
        return min(reason.tier for reason in self.reasons)
```

构造不变量：

1. `reasons` 非空；
2. 所有 reason 的 `stage_id` 等于 candidate 的 `stage_id`；
3. reason ID 不重复；
4. `effective_tier` 不存储，始终由 reasons 推导；
5. 所有原始 reasons 必须保留，不能只保留最终 tier；
6. candidate 聚合不得覆盖或删除 reason scope。

# 9. Structural Impact 与 Boundary Span

## 9.1 Structural Impact Registry

```
@dataclass(frozen=True, kw_only=True)
class StructuralImpactRegistry:
    registry_version: str
    entries: tuple[
        tuple[ConclusionId, StructuralImpactLevel], ...
    ]
```

定义：

```
GLOBAL_DECISION
- Top-N 根因
- 跨阶段排序
- 全局商业结论
- 最终摘要或主要建议

STAGE_DECISION
- stage severity
- stage 主诊断
- stage 主要改进建议

LOCAL_FACT
- supporting fact
- 不改变 stage/global 结论
```

impact 由 `affected_conclusion_ids` 查 registry 后取最大值。规则不得直接提供自由分数。

------

## 9.2 Decision Boundary Span

使用正式 severity rank，而不是自然语言判断。

```
@dataclass(frozen=True, kw_only=True)
class PhaseCPriorityContext:
    structural_impact_registry: StructuralImpactRegistry
    severity_order: tuple["Severity", ...]
    canonical_stage_order: tuple[StageId, ...]
```

计算：

```
span = max(rank(outcome)) - min(rank(outcome))
```

来源：

- `FloorCeilingConflictReason`：使用 floor 和 ceiling；
- `StateConflictReason`：使用 `admissible_severities`；
- `UncertainFactBoundaryReason`：使用 `admissible_severities`；
- `InsufficientStrengthStructuralReason`：没有 boundary span，返回 `None`。

未知 span 在相同 impact 下排在已知 span 后面，不能伪装为 0。

------

# 10. 确定性排序函数

不再使用一个模糊的统一 `tie_breakers` 字段。不同 tier 使用不同比较函数。

## 10.1 Tier 1

优先顺序：

1. structural impact；
2. boundary span 是否已知；
3. boundary span 大小；
4. conflict type；
5. canonical stage order；
6. stable reason ID。

Conflict type：

```
floor-ceiling conflict = 2
state conflict         = 1
```

伪代码：

```
def tier1_priority_key(
    reason: StateConflictReason | FloorCeilingConflictReason,
    context: PhaseCPriorityContext,
) -> tuple[object, ...]:
    impact = structural_impact(reason, context)
    span = decision_boundary_span(reason, context)

    conflict_rank = (
        2
        if isinstance(reason, FloorCeilingConflictReason)
        else 1
    )

    return (
        -impact.value,
        span is None,
        -(span or 0),
        -conflict_rank,
        stage_index(reason.stage_id, context),
        reason.reason_id,
    )
```

## 10.2 Tier 2

```
def tier2_priority_key(
    reason: UncertainFactBoundaryReason,
    context: PhaseCPriorityContext,
) -> tuple[object, ...]:
    impact = structural_impact(reason, context)
    span = decision_boundary_span(reason, context)

    return (
        -impact.value,
        span is None,
        -(span or 0),
        stage_index(reason.stage_id, context),
        reason.reason_id,
    )
```

## 10.3 Tier 3

```
def tier3_priority_key(
    reason: InsufficientStrengthStructuralReason,
    context: PhaseCPriorityContext,
) -> tuple[object, ...]:
    impact = structural_impact(reason, context)

    return (
        -impact.value,
        stage_index(reason.stage_id, context),
        reason.reason_id,
    )
```

## 10.4 Candidate 排序

一个 candidate 的排序基准，是其 `effective_tier` 中优先级最高的 reason。

同一个 candidate 内，所有与 `effective_tier` 相同的 reasons 都属于有效 trigger reasons；较低 tier reasons 不会自动进入 review scope。

# 11. Phase C Budget Policy

```
@dataclass(frozen=True, kw_only=True)
class PhaseCBudgetPolicy:
    policy_version: PhaseCBudgetPolicyVersion
    max_reviewed_stages: int
    tier1_overflow_policy: Tier1OverflowPolicy
    lower_tier_reservation_policy: (
        LowerTierReservationPolicy
    )
    priority_context: PhaseCPriorityContext
```

V1 固定政策：

```
PHASE_C_BUDGET_V1 = PhaseCBudgetPolicy(
    policy_version=PhaseCBudgetPolicyVersion.TIERED_V1,
    max_reviewed_stages=2,
    tier1_overflow_policy=(
        Tier1OverflowPolicy.STRICTLY_PREEMPT_LOWER_TIERS
    ),
    lower_tier_reservation_policy=(
        LowerTierReservationPolicy.ONLY_AFTER_TIER1_SATISFIED
    ),
    priority_context=...,
)
```

分配规则：

1. Tier 1 stage candidates 先于所有 Tier 2/3。
2. Tier 1 数量达到或超过 capacity 时，不给 Tier 2/3 保留名额。
3. Tier 1 超预算时，只在 Tier 1 内进行确定性排序。
4. Tier 1 全部满足后，剩余名额分配给 Tier 2。
5. Tier 3 只使用 Tier 1/2 都未占用的残余名额。
6. 未执行 reason 不得丢失。
7. 未执行 Tier 1 reason 必须进入 `unserved_mandatory`。
8. budget 以不同 stage 数量计数，而不是 reason 数量。
9. 一个 selected stage 在一个 plan 中最多出现一次。

# 12. Review Scope 与 Allocation

```
@dataclass(frozen=True, kw_only=True)
class PhaseCAllocation:
    allocation_id: AllocationId
    candidate_id: CandidateId
    stage_id: StageId
    slot_index: int

    trigger_reason_ids: tuple[ReasonId, ...]
    co_reviewed_reason_ids: tuple[ReasonId, ...]

    review_scope: PhaseCReviewScope
    priority_trace: tuple[str, ...]
```

规则：

## 12.1 Trigger reasons

`trigger_reason_ids` 是该 candidate 中所有满足：

```
reason.tier == candidate.effective_tier
```

的 reasons。

它们每一条都独立满足当前 tier 的资格，不是因为 stage 已经入选才顺带带入。

`review_scope` 等于所有 trigger reason scopes 的精确并集。

## 12.2 Co-reviewed reasons

较低 tier reason 只有在以下条件全部成立时，才能进入 `co_reviewed_reason_ids`：

- scope 是 trigger scope 的子集或完全相同；
- 不增加 fact；
- 不增加 evidence；
- 不增加 constraint evaluation；
- 不增加 allowed patch path；
- 不要求判断新的结构性结论。

Co-reviewed reason 不得扩大 `review_scope`。

## 12.3 未包含 reasons

其余 reasons：

- Tier 1：进入 `unserved_mandatory`；
- Tier 2/3：进入 `deferred_optional`。

同一个 stage 被选中，不代表该 stage 上所有问题都获得了复核授权。

# 13. Phase C Plan

```

    SCOPE_NOT_INCLUDED = "scope_not_included"

    deferral_code: DeferralReasonCode


@dataclass(frozen=True, kw_only=True)
class UnservedMandatoryReason:
    reason_id: ReasonId
    deferral_code: Literal[
        DeferralReasonCode.CAPACITY_EXHAUSTED,

@dataclass(frozen=True, kw_only=True)
class PhaseCPlan:
```

Plan 不变量：

1. `len(selected) <= capacity`。
2. selected stage 不重复。
3. selected、unserved mandatory、deferred optional 构成 qualified reasons 的完整分区。
4. 任一 reason ID 只能出现一次。
5. 存在未选 Tier 1 stage candidate 时，selected 中不能存在 Tier 2/3 candidate。
6. 输入 reason 或 candidate 顺序变化不得改变 plan。
7. `priority_trace` 必须足以重建排序决定。
8. raw signals 和 observed-only signals 不进入上述分区。


- severity resolver 只能生成 resolver 来源的 raw signals；
- evidence validator、deterministic check、model self-report 的 signals 在 provisional result 层汇总；
- candidate qualifier 负责 raw signals → qualified reasons；
- candidate aggregator 负责 reasons → stage candidates；
- planner 负责 candidates → allocations。

# 19. `unserved_mandatory` 的产品政策

Tier 1 reason 因预算不足未执行时，默认：

```
PublishableDegraded(
    reason_codes=(
        "phase_c_tier1_unserved_due_budget",
    ),
    affected_stage_ids=(...),
)
```

具体行为：

1. 保留 resolver 当前 fallback。
2. 标记 resolution 未完全解决。
3. 继续生成报告。
4. 受影响 stage 的结论降低确定性。
5. 依赖该 stage 的建议不得伪装为确定性结论。
6. 该 stage 不得作为全局结论的唯一决定依据。
7. audit 必须记录排序、挤兑、budget policy 和未服务原因。

以下情况才允许 `PublicationBlocked`：

- 最终发布合同无法成立；
- 输入与产物身份无法验证；
- 存在无法以降级语义安全表达的逻辑矛盾；
- 安全或合规政策明确要求阻断；
- 报告继续发布会实质性误导用户。

**预算耗尽本身不能单独造成 blocked。**

# 20. FinalizationKernel 唯一公开接口

```
class FinalizationKernel:
    def provisional_pass(
        self,
        value: FinalizationInput,
    ) -> ProvisionalFinalizationResult:
        repaired = self._repair(value)
        validated = self._validate_hard_facts(repaired)
        constrained = self._collect_constraints(validated)
        resolved = self._resolve_severity(constrained)
        result = self._synthesize_candidates(resolved)

        assert result.kernel_trace.stage_ids == (
            PROVISIONAL_SEQUENCE
        )
        return result

    def final_pass(
        self,
        value: PostPhaseCFinalizationInput,
    ) -> TerminalFinalizationResult:
        repaired = self._repair(value)
        validated = self._validate_hard_facts(repaired)
        constrained = self._collect_constraints(validated)
        resolved = self._resolve_severity(constrained)
        result = self._terminalize(
            resolved,
            value.phase_c_outcome,
            value.phase_c_plan,
        )

        assert result.kernel_trace.stage_ids == FINAL_SEQUENCE
        return result
```

内部步骤不得作为公共生产接口导出。

## 22.2 Policy Conformance

用于 PR-PC1/PC2。

至少包含：

| 场景                                    | 预期                                     |
| --------------------------------------- | ---------------------------------------- |
| 仅模型自报低置信                        | observed only，不产生 reason             |
| 模型自报 + 同 scope state conflict      | Tier 1                                   |
| 模型自报 + 不同 stage conflict          | 不关联                                   |
| 模型自报 + 同 stage 不同 fact/evidence  | 不关联                                   |
| `STATE_CONFLICT + TIER_3` JSON          | 解析失败                                 |
| 构造 `StateConflictReason(tier=TIER_3)` | 构造失败                                 |
| 3 个 Tier 1、capacity 2                 | 2 个 selected，余下 Tier 1 进入 unserved |
| 1 个 Tier 1 + 2 个 Tier 2、capacity 2   | Tier 1 + 最高优先 Tier 2                 |
| 2 个 Tier 1 占满预算                    | Tier 2/3 无保留名额                      |
| 同 stage Tier 1 + 无关 Tier 3           | Tier 3 不扩大 scope                      |
| 低 tier scope 是 trigger scope 子集     | 可以 co-review                           |
| 输入顺序随机变化                        | plan 不变                                |
| allocation 技术重试                     | 不重复扣预算                             |
| final pass 产生新信号                   | terminal issue，不重新 planner           |

性质测试：

```
selected stage 数量 <= capacity

未选 Tier 1 存在时，
不得选择 Tier 2/3 stage candidate

qualified reason 必须被完整分区：
served / unserved mandatory / deferred optional

同一 reason 不得重复出现

候选输入顺序不得影响 plan

review scope 不得被 co-reviewed reason 扩大

final result 类型中不存在 candidate 字段
```

# 最终收口

这份 ADR 明确选择了判别联合，并消除了三份旧文档之间的主要冲突：

| 冲突点                                            | 最终定义                                                     |
| ------------------------------------------------- | ------------------------------------------------------------ |
| `QualifiedPhaseCReason` 是通用 dataclass 还是联合 | 判别联合                                                     |
| `reason_code` 与 `tier` 是否可自由组合            | 不可；由具体类型固定，且不是构造参数                         |
| 模型自报能否独立成候选                            | V2 下不能                                                    |
| Legacy 候选是否伪装成 V2 reason                   | 不能；两种 candidate set 类型隔离                            |
| candidate 的 effective tier 如何存储              | 不存储，动态推导                                             |
| 同 stage 的低 tier reason 是否扩大 scope          | 不能；仅 scope 子集可 co-review                              |
| `PhaseCAllocation` 使用哪个字段版本               | `trigger_reason_ids + co_reviewed_reason_ids + review_scope` |
| plan 的 deferred 与 unserved 是否重叠             | 不重叠，构成完整分区                                         |
| tie-breaker 是否使用统一四维名称                  | 不使用；按 tier 定义具体比较函数                             |
| final pass 是否可以产生新候选                     | 不可以，返回类型无 candidate 字段                            |
| Tier 1 未服务是否阻断发布                         | 默认降级发布                                                 |
| `generation_id` 含义                              | 删除；使用 run/attempt/step execution 身份                   |
| V2 是否属于 PR-0A-Core                            | 不属于，blind 后条件性实施                                   |

**这版可以冻结。** 后续实现不得再从 frame1、frame2 或 new3 单独复制类型；所有同名定义以 ADR-006 为准。
